# Modernization architecture proposal

## Recommendation

Use one monorepo with three explicit source roles:

```text
reference/original-0.3.0/    frozen runnable oracle source
packages/msbwt-modern2/      independently built Python 2.7 distribution
packages/msbwt-modern3/      independently built current Python 3 distribution
compat/                      format specs, fixture manifests, goldens, differential harness
tests/                       shared black-box scenarios plus target-specific API tests
benchmarks/                  reproducible datasets and operation drivers
docs/                        provenance, compatibility, migration, security, releases
```

Do not create this layout until the legacy oracle and initial goldens are working. The paths are an architectural destination, not an implementation performed by this audit.

The frozen source should be byte-identical to audited commit `7503346` (or reference that commit without duplication) plus only the minimum external harness/container files needed to execute it. Never “repair” the oracle; record its failures. Build modern2 and modern3 in separate environments because both distributions should initially retain `MUS`, `MUSCython`, and the `msbwt` command and therefore cannot safely coexist in one site-packages environment.

Share contracts before sharing runtime source. The two ports should share format specifications, fixture inputs, expected logical results, raw hashes, differential-test protocols, benchmark definitions, and documentation. During semantic preservation, allow their Python and Cython sources to diverge where Python 2/3 syntax, bytes handling, Cython language level, build tooling, or dependency APIs demand it. Consolidate proven-identical algorithms later only when doing so does not blur target semantics.

## Why this fits this repository

The repository is not one clean Python layer around one Cython kernel. It has overlapping pure/Cython algorithms, Python 2 implicit-relative imports, `bytes` and `char *` signatures, source-visible Python 2 division dependencies, stale APIs, mode-dependent on-disk formats, and old C generated by two Cython generations. A “single source plus six imports” approach would hide meaningful runtime differences and encourage simultaneous port/refactor work.

A monorepo still provides the strongest compatibility control:

- every change can run one writer/reader matrix across legacy, modern2, and modern3;
- goldens and format specifications cannot silently drift between repositories or long-lived branches;
- security fixes and intentional deviations can be documented once while implemented appropriately per target;
- release provenance and scientific attribution remain unified;
- common low-level algorithm code may be extracted later based on evidence rather than assumed shareability.

## Alternatives considered

| Design | Benefit | Codebase-specific cost | Verdict |
|---|---|---|---|
| modern3 main branch plus long-lived modern2 branch | Minimal tree restructuring | Compatibility tests, format fixes, security patches, and goldens drift; cross-reader CI becomes awkward; Python 2 branch risks neglect | Reject as primary design |
| two repositories | Complete release independence | Duplicates issue history, provenance, format governance, fixtures, and differential infrastructure | Reject |
| one fully shared source tree with compatibility helpers | Least apparent duplication | Python 2 cannot parse modern annotations/syntax; Cython 2/3 semantics and bytes/path APIs differ; conditionals invade critical code | Reject for initial port; reassess after parity |
| two package roots in one monorepo | Explicit toolchains and release units with central compatibility assets | Some temporary duplication and coordinated fixes | Recommend |
| generate both ports from templates | Can force algorithm identity | Generated-source debugging and line mapping complicate Cython; template errors become another compatibility layer | Avoid unless later repetition justifies it |

## Distribution and namespace design

- Distribution/project names are `msbwt-modern2` and `msbwt-modern3`.
- Initially expose legacy import packages `MUS` and `MUSCython` and command `msbwt` in each environment.
- Add a modern namespace only as an additive facade after compatibility is stable. Do not move legacy imports and rely solely on redirects without import-level regression tests.
- Define Python 3 boundary policy explicitly: user-facing sequence/path APIs should accept documented text and/or bytes forms, convert once, and keep Cython kernels on validated bytes/numeric buffers. Return-type mapping from Python 2 `str` must be decided by tests and migration policy.
- Keep package build metadata, dependency locks, and wheels separate. A workspace-level orchestrator may invoke both but must not force Python 2 tooling through modern Python build backends.

## Modern2 toolchain

- Python 2.7 in a digest-pinned legacy Linux container is the Tier 1 reference.
- Select the newest Cython 3.0.x release that empirically builds the full extension set on Python 2.7; set `language_level=2` explicitly and pin every build dependency.
- Determine newest practical Python-2-compatible NumPy, pysam, setuptools/pip/wheel, compiler, and manylinux baseline by a tested compatibility matrix. Do not infer “latest compatible” from metadata alone.
- Preserve Python 2 string/integer semantics intentionally. Add explicit `cdivision` or `//` only after tests demonstrate the original result.
- Additional platforms are best effort and cannot be promised until built and tested. A source-build route matters more than broad wheel coverage.

## Modern3 toolchain

- Start with the latest stable CPython available when implementation begins, latest practical stable NumPy/pysam/Cython/build backend, and a supported C compiler on each Tier 1 platform.
- Port imports, bytes/text/path boundaries, integer division, iterator APIs, pysam, and NumPy APIs without redesigning algorithms.
- Add recent Python 3 versions only after latest-Python compatibility passes; keep the matrix small enough that compiled behavior is actually tested.
- Use PEP 517 build isolation, declarative metadata, wheels, and platform CI. The compatibility namespace remains first-class even if a typed modern facade is added.

Exact future versions are deliberately not frozen in this proposal because “latest stable” is time-sensitive. Record resolved versions and evidence when implementation starts.

## Generated C policy

### modern2

Commit C generated from the pinned Cython 3.0.x toolchain, alongside `.pyx`/`.pxd`, for these reasons:

- Python 2 build isolation and Cython bootstrapping are fragile and likely to worsen;
- an sdist should remain buildable in the pinned legacy environment without downloading/running Cython;
- checked-in output preserves a reviewable last-known generator result for a sunset ecosystem.

Never hand-edit it. CI should regenerate in the pinned container and require a clean diff. Wheels should be built from the same source/tag/toolchain. Record compiler and generator versions in release provenance.

### modern3

Do not keep generated C as a hand-maintained Git source. Build wheels from `.pyx` in pinned/reproducible CI. Release sdists should include generated C produced by the release job so offline/HPC consumers can compile without Cython at install time, while VCS/editable builds may require the declared Cython build dependency. CI must compare regeneration and test both wheel and sdist paths.

This split is based on Python 2 bootstrapping and release longevity, not style preference. Preserve the original generated C unchanged in the frozen reference.

## Format architecture

Before porting writers, create a versioned, language-neutral directory-format specification that covers:

1. every primary, provenance, derived, recovery, and temporary filename;
2. `.npy` magic/version/header bytes, dtype descriptor, shape, C/Fortran order, and payload order;
3. headerless files whose `.npy` suffix is misleading;
4. RLE digit order, LZW reader format, interleave bit order, sequence sorting/tie-break rules, and dollar-ID meaning;
5. validity rules, corruption response, partial-write detection, rebuild behavior, and reader selection when formats coexist.

Do not add an in-directory manifest in a way that prevents old readers. An additive manifest may be safe because old readers ignore unknown names, but prove this for cleanup/glob paths first. New writers should retain legacy primary files; new metadata can advertise validation/version information to modern readers.

For bit equality across NumPy versions, choose either a dedicated legacy-compatible `.npy` writer/header routine or pin a writer library whose exact bytes match the oracle. Payload equality alone does not satisfy the stated contract.

## API layering for the ports

Each target should evolve toward:

1. a compatibility facade preserving modules, names, signatures, default behavior, and CLI;
2. validated Python boundary code for text/bytes, paths, process counts, formats, and errors;
3. Cython kernels with fixed-width integer types, explicit directives, and narrow typed interfaces;
4. format reader/writer modules shared conceptually through the specification and conformance suite;
5. optional modern3-only typed APIs that delegate to the compatibility layer or kernels.

Do not combine this layering work with algorithm optimization. First reproduce results, then correct documented defects, then measure, then optimize one operation at a time.

## Platform plan

Modern3 Tier 1 CI should ultimately cover Linux x86-64, Windows x86-64, macOS Apple Silicon, and an HPC-representative Linux source build. Linux ARM64, macOS Intel, WSL, and Conda become supported only after evidence. Platform tests must include large-index type checks, binary-mode file I/O, path Unicode/spaces, read-only datasets, multiprocessing start methods, wheel import, and dataset exchange.

Modern2 Tier 1 is the legacy Linux container. Other platforms are explicitly experimental until the exact Python 2, NumPy, compiler, and pysam combination succeeds. Do not let modern2 platform constraints weaken modern3's native support.

## Implementation sequence

1. Reconstruct and freeze the legacy Linux oracle; capture tiny goldens and current failures without source repair.
2. Add shared black-box harness, format specification, golden manifests, and reader/writer matrix.
3. Create package roots and build modern2 first enough to reproduce the oracle with Cython 3.0.x; separate build-semantic changes from defect fixes.
4. Port modern3 to the latest CPython with equivalent files/API/CLI, then add recent Python versions and Tier 1 platforms.
5. Apply documented correctness/security fixes to both where viable; publish `COMPATIBILITY.md`, migration notes, and releases.
6. Establish benchmark baselines, profile, and only then optimize with compatibility tests held fixed.

Each numbered item is a release/commit series, not one commit.
